# ch01 · 观察系统：建立进程地图（实操笔记）

> 完成于 2026-11-15 · 方法：纯命令观察，零源码改动 · 模拟器实测数据

## 1. 进程家谱（实测 PID）

```
init (PID 1) ← 内核拉起的第一个进程
 ├── servicemanager (1528)     Binder 电话簿：名字 → 服务遥控器
 │   (hwservicemanager/vndservicemanager 是硬件/厂商服务各自的电话簿)
 ├── zygote64 (3470) ──┬─ system_server (3503)   ~165 个系统服务的家
 │                     ├─ com.android.settings (3793)          ← fork 现场围观
 │                     └─ com.android.settings.intelligence
 ├── zygote (3471) ─────── webview_zygote（32 位孵化线）
 └── logd / adbd / ...
```

关键认知：
- **system_server 也是 zygote 孵出来的**（PPID=3470 实测）
- app 进程不是"安装"出来的，是 zygote **fork** 出来的 → 出生自带 ART + 已加载的 framework 类，这是 app 启动快的根本原因
- 全系统共约 166 个进程，绝大部分是 app

## 2. service list：getSystemService 的真相

- 共 **165 个** Binder 服务
- 接口名全是 `I` 开头的 AIDL 接口（IActivityManager/IAlarmManager/IWindowManager...）→ **与 app 里写的 AIDL 是同一套机制**
- `getSystemService(ALARM_SERVICE)` 本质 = 拿名字查 servicemanager → 得到 Binder 代理（遥控器）→ 每次调用跨进程打到 system_server 真身

## 3. dumpsys 三板斧（实测输出摘要）

| 命令 | 看什么 |
|---|---|
| `dumpsys activity activities \| grep -E "Hist #\|mResumedActivity"` | AMS 的 Task 栈，谁是 mResumedActivity |
| `dumpsys window \| grep -iE "mcurrentfocus\|mfocusedapp"` | WMS 眼中持有屏幕的窗口 |
| `dumpsys window windows \| grep "Window #"` | 全部窗口，按栈序排列 |

实测窗口栈：`Wallpaper → Launcher → Settings(focus) → Assist → StatusBar → NavBar`

**惊艳细节**：WMS `mFocusedApp` 的 token 里嵌着 `ActivityRecord{e494f44 ... t3}`，与 AMS dump 里的 `e494f44` 是同一对象引用——两个服务通过 token 共享对 Activity 的认知，和 ch06 将读到的源码完全对得上。

## 4. 踩坑记录

- **Android 10 里 `mCurrentFocus` 不在 `dumpsys window windows` 里**（那是逐窗口列表），要查 `dumpsys window` 主报告
- dumpsys 字段名每版都会变，姿势：先看原始输出再 grep，别硬记字段名

## 5. 验收自测（合上笔记回答）

1. 点一下桌面图标，哪些进程参与？各自做什么？
   > Launcher 收点击 → AMS(system_server) 决策 → zygote fork 新进程 → 新进程建 Activity → WMS 排窗口焦点 → 全程查 servicemanager 找彼此
2. app 启动为什么快？
   > fork zygote，继承已加载的 ART 和 framework 类
3. `getSystemService()` 返回的对象是什么？
   > Binder 代理（遥控器），真身在 system_server

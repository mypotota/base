## 一、修复 Settings 启动闪退

### 现象

模拟器（自编译 aosp8 镜像）打开「设置」即闪退。

### 定位

Settings 的入口列表由 `SettingsActivity` 构建，每个入口注册时都会调用自己的 `isAvailable()`
决定是否显示。相关代码：

- `packages/apps/Settings/src/com/android/settings/SettingsActivity.java:845`
  —— 构建入口时调用 `WifiDisplaySettings.isAvailable(this)`
- 崩溃点在 Wi-Fi Display（投屏）相关链路：模拟器上该功能依赖的
  DisplayService / WifiP2p 服务环境不完整，走到 `WifiDisplaySettings` 就崩

### 修复（commit `49f78073`）

把 WFD 入口直接屏蔽（`isAvailable` 返回 false），恢复 Settings 可用：

```java
// packages/apps/Settings/src/com/android/settings/wfd/WifiDisplaySettings.java
public static boolean isAvailable(Context context) {
    return false;
    // return context.getSystemService(Context.DISPLAY_SERVICE) != null
    //        && context.getSystemService(Context.WIFI_P2P_SERVICE) != null;
}
```

要点：

- **代价**：设置里不再显示「投屏」入口。模拟器上无伤大雅，真机/深度调试需求再回来深挖根因
- **根因未深挖（诚实记录）**：原判断本身只是两个 `getSystemService` 非空检查，理论上不会
  自己崩；真正的崩溃栈应在 `SettingsActivity` 入口构建的后续逻辑里。当前是止损式修复，
  后续拿到完整 tombstone 后可在 chNN 补一篇根因分析
- **版本管理**：`~/aosp/packages` 是独立 git 仓库（2026-11-17 移除 repo 后新建，当前有
  `init` 与本次修复两个提交），改动直接 `git add/commit`，不走知识库同步脚本

### 验收标准

- [x] `git log` 看到修复提交
- [x] 模拟器打开设置不再闪退（见文末验收实录）

## 二、整编：把修复编进镜像

### 翻车现场：`make packages` ❌

```
ninja: error: unknown target 'packages', did you mean 'mm/packages'?
#### failed to build some targets (33 seconds) ####
```

**原因**：`make` 后面跟的必须是**编译目标**（`droid`、模块名如 `Settings`、`snod` 等），
`packages` 只是源码目录名，不是编译目标。想"编译 packages 目录"这个直觉是错的——
AOSP 的编译单元是模块（Android.mk/Android.bp 里定义），不是目录。

### 正确姿势（整编 = 全量/增量同一个命令）

```bash
cd ~/aosp
source env_aosp8.sh aosp_x86_64-eng   # 每个新终端第一句！见下文环境坑
make -j10                              # 不带目标 = 默认 droid（整编）
```

- 首次整编：本机已在此前完成（12:20→14:35，有效约 100 分钟，见前置笔记）
- **增量整编实录（2026-11-17 23:00）**：改完 Settings 提交后直接 `make -j10`，
  **53 秒完成**——只重编了 Settings（Java → desugar → proguard → dex → 打包 APK），
  然后自动重打 `system.img` / `system-qemu.img` / `vendor.img`。改一个 app 就是这个量级
- 单模块编译：`make Settings`（只编 Settings 不重打镜像；配合 ch02 的
  `adb remount && adb sync system` 部署，适合反复调试）

### 验证修复真的进了镜像

看时间戳（最简单可靠）：

```bash
ls -l out/target/product/generic_x86_64/system/priv-app/Settings/Settings.apk
ls -l out/target/product/generic_x86_64/system.img
# 两者 mtime 晚于 git commit 时间即已包含修复
```

⚠️ **产物目录是 `generic_x86_64` 不是 `aosp_x86_64`**：lunch 的产品名是
`aosp_x86_64`，但 `PRODUCT_DEVICE=generic_x86_64`，out 下镜像按后者存放。找镜像别找错目录。

### 环境坑（当天实测二次踩雷）

在另一个终端手动 `source build/envsetup.sh && lunch` 后直接 `m`，连续踩死：

1. `Environment variable ANDROID_COMPILE_WITH_JACK was modified (false => ), regenerating...`
   —— 构建系统发现环境变量与上次不同，把上千个目标全部重新生成
2. `FAILED: setup-jack-server`（curl server.pem 不存在）—— 没禁 Jack，8.1 默认的
   Jack 编译器在新系统上必挂（前置笔记错误⑤）
3. `normalize_path.py SyntaxError: print os.path...` —— 没 py2 shim，py2 脚本撞上
   python 3.14（前置笔记错误⑥）

**结论（本系列铁律）**：Ubuntu 26.04 上手动 source envsetup+lunch 编译 aosp8 必然失败，
必须 `source ~/aosp/env_aosp8.sh aosp_x86_64-eng`。它固化了 5 项环境修正：
python2 shim PATH / `LC_ALL=C` / `ANDROID_DATA` / `WITH_DEXPREOPT=false` / 禁 Jack。
看到 "Environment variable ... was modified, regenerating" 就是两个终端环境不一致的信号。

## 三、启动模拟器

```bash
cd ~/aosp && source env_aosp8.sh aosp_x86_64-eng
emulator -no-snapshot -gpu swiftshader_indirect -no-boot-anim -memory 2048
```

- `emulator` 命令 **不需要手动加 PATH**：`envsetup.sh` 已自动把
  `prebuilts/android-emulator/linux-x86_64` 加入 PATH（注意目录名是**连字符**，
  env_aosp8.sh 旧注释写成下划线导致找不到命令，已修正）
- `-writable-system`：需要改 system 分区（`adb remount`）时必加（沿用 aosp10 系列经验）
- 软渲染 `swiftshader_indirect`：无 GPU 直通需求，最稳
- 验证开机：

```bash
adb devices                                          # 看到 emulator-5554 device
adb -e shell getprop sys.boot_completed              # 1 即开机完成（有真机时永远带 -e）
adb -e shell getprop ro.build.fingerprint            # eng.<用户名>.<时间戳> = 自编镜像铁证
```

### 坑①：实例锁

```
emulator: ERROR: There's another emulator instance running with the current AVD '<build>'. Exiting...
```

旧实例没关干净就会这样。先关掉旧实例（正常关窗，或找到 qemu 进程 kill；
`SIGTERM` 无效时 `kill -9 <qemu PID>`），再启动。

### 坑②：无窗口（headless）启动会卡死在开机 ⚠️ 当天新发现

`-no-window` 启动后 `sys.boot_completed` 永远等不到（>15 分钟）。诊断过程：

1. `ps -A` 发现只有 zygote64/zygote，**system_server 始终没起**
2. `cat /proc/<zygote64 pid>/wchan` → `SyS_getrandom`：zygote 阻塞在 getrandom 系统调用，
   等**熵池初始化**
3. `cat /proc/sys/kernel/random/entropy_avail` → `0`：跑了 15 分钟熵池还是 0

**根因**：guest 内核 3.18 下，用户态写 `/dev/random` 只混入字节不记熵，熵只能靠硬件中断
积累；tickless 空闲 guest + 无窗口（无渲染、无输入）≈ 零中断 → 熵池永远攒不够 →
zygote 永远等不到随机数 → 开机卡死。**带窗口启动时 SurfaceFlinger 持续渲染 + 交互
产生大量中断，熵很快攒满**（实测 ~1 分钟开机），所以平时没暴露。

**解法**：带窗口启动（本系列默认姿势）。若真有 headless 需求，思路是给 guest 记熵
（如 root 下用 `ioctl RNDADDTOENTCNT` 注入，未实测）；已把警告写进 env_aosp8.sh 注释。

## 常见坑速查表（aosp8 起始篇版）

| 坑 | 信号 | 解法 |
|---|---|---|
| `make packages` | `ninja: error: unknown target 'packages'` | 整编 `make`；单模块 `make Settings`；目标名≠目录名 |
| 裸 source envsetup 编译 | Jack curl 报错 + py2 SyntaxError | `source ~/aosp/env_aosp8.sh`（铁律） |
| 两终端环境不一致 | `Environment variable ... was modified, regenerating` | 统一用 env_aosp8.sh，换终端必重新 source |
| 找不到 emulator 命令 | `command not found` | 没先 source 环境；目录名是 `linux-x86_64`（连字符） |
| 模拟器起不来：实例锁 | `another emulator instance running ... AVD '<build>'` | 关旧实例（TERM→无效则 -9 qemu PID） |
| 模拟器起不来：卡开机 | `sys.boot_completed` 永不=1，zygote 在 `SyS_getrandom` | 别用 `-no-window`；带窗口启动喂熵 |
| 修复没生效 | 行为和改之前一样 | 查 `Settings.apk`/`system.img` mtime 是否晚于代码修改；忘整编或镜像目录找错（是 `generic_x86_64`） |
| pkill/killall 自杀 | 后台任务瞬间失败且日志为空 | 模式串用字符类破坏自匹配：`pkill -f 'repo sy[n]c'`（继承笔记坑②） |

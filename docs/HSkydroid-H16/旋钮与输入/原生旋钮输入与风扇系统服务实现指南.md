# H16 原生旋钮输入与风扇系统服务实现指南

适用于 `~/aosp` 的 `skydroid_arowana_rc-userdebug`。第一阶段把 AUX1、AUX2 接入 Android 的标准输入。第二阶段在 Framework 发布风扇服务，提供状态查询和控制。建议依次验证，便于定位构建、启动和运行时故障。

## 已确认的实机条件

- `rc_service` 已能在开机后启动，从 `/dev/ttyS0` 接收数据，并将通道帧发送到抽象 Unix 数据报套接字 `@uart0app`。
- H16 输入测试已经收到 16 路值。零基下标 `10` 曾在 `1050–1950` 间变化。AUX1、AUX2 各自所用的下标、方向和端点须分别实测。
- 实机已有 `/dev/uinput`，模式为 `0660`，属主属组为 `system:bluetooth`，SELinux 标签为 `uhid_device`。
- 风扇由 GPIO174 控制。实机已确认输出 `1` 时风扇转动，测试后读回 `0`。服务读这个节点能确认 GPIO 电平，风扇物理转速需要测速反馈，当前未确认存在该反馈。参见 [风扇实测](../风扇控制/风扇实测与自动温控修复.md) 和 [旋钮接口](AUX1与AUX2旋钮接口.md)。

## 一、让 Android 原生接收两个旋钮

```text
/dev/ttyS0 → rc_service → @uart0app → h16_input
    → /dev/uinput → /dev/input/eventN → InputReader → MotionEvent
```

### 改哪些源码

以下路径以 `~/aosp` 为起点，文件名为建议命名。

| 文件 | 改动 |
| --- | --- |
| `device/skydroid/arowana_rc/h16_input/Android.mk` 和 `h16_input.cpp` | 新建原生可执行模块。监听数据报、验证数据帧、提取两个通道、注册虚拟设备。 |
| `device/skydroid/arowana_rc/legacy-init/h16_input.rc` | 由 init 在 `rc_service` 启动后拉起和管理 `h16_input`。 |
| `device/skydroid/arowana_rc/skydroid_arowana_rc.mk`、`legacy-init.mk` | 加入模块、init 配置及专用 `.kl` 的打包项。 |
| `device/skydroid/arowana_rc/sepolicy/` | 增加服务域和可执行文件标签，允许该域操作 uinput，允许 `rc_service` 向该域发送 Unix 数据报。核对现有 `rc_service.te`。 |
| `frameworks/native/services/inputflinger/EventHub.cpp` | 为只有两个绝对轴的 H16 虚拟设备增加精确识别条件。 |
| `device/skydroid/arowana_rc/keylayout/` 下新增设备专用 `.kl` | 将选用的 Linux 轴映射为 Android 轴。例如将 `ABS_RX`、`ABS_RY` 映射为 `GENERIC_1`、`GENERIC_2`。 |

### 实现顺序

1. **记录标定数据。** 先用已有 Demo，保持其他控件静止，分别慢转 AUX1 和 AUX2 到两端再转回。记录每个旋钮的零基下标、左端和右端读数、机械中位、空闲噪声。把结果作为设备配置固化，首帧使用实际位置，后续只上报有意义的变化。SDK 只用于这一步的对照测量。
2. **接入通道帧。** 原生进程用 `AF_UNIX` 和 `SOCK_DGRAM` 绑定抽象地址，`sun_path` 首字节为 NUL，随后是 `uart0app`，地址长度应与发送方一致。实机跟踪见过 44 字节的 `SKYDROID:` 通道帧。先逐字段核对原厂解析逻辑及抓包，验证帧类型、长度、完整性校验和整数字节序，再从两项确认的下标取值。用几个已知位置的通道帧对照 Demo 输出，丢弃校验失败和截断的包。专用 SELinux 域、发送权限和可行时的 Unix 凭据检查用来限制输入来源。
3. **切换套接字所有者。** SDK Demo 和 `h16_input` 都会绑定 `@uart0app`。标定时停桥接服务，验证原生输入时结束 SDK Demo。以后若要给其他组件共享原始值，由同一个接收进程分发，避免两个进程争用地址。
4. **注册两个轴。** 用 `BUS_VIRTUAL`、固定设备名和设备专用标识注册 `EV_ABS` 的两个轴，填各自报告范围及抖动参数。通过运行时检查 uinput 支持的 ioctl 版本，老内核可使用写入 `uinput_user_dev` 后调用 `UI_DEV_CREATE` 的方式。每次更新连续写入变化的绝对轴，再写 `SYN_REPORT`。退出时销毁虚拟设备。 [Linux uinput 文档](https://www.kernel.org/doc/html/latest/input/uinput.html)
5. **补 Android 8.1 的分类。** 本树 `EventHub.cpp` 的 joystick 分支以 `haveGamepadButtons` 为前置条件。仅实现两个旋钮时，在这个分支旁依据虚拟总线、固定设备标识和预期的轴能力进行精确匹配，然后进入现有绝对轴分类循环。只为这台虚拟设备开放，避免带绝对轴的其他设备被重新分类。匹配设备标识命名的 `.kl` 并只配置这两个轴。应用在前台检验 `SOURCE_JOYSTICK`，通过 `onGenericMotionEvent()` 和 `getAxisValue(AXIS_GENERIC_1/2)` 读值。通过 `getMotionRange()` 获取 Android 坐标范围，百分比按该范围换算。 [Android 键位映射文档](https://source.android.com/docs/core/interaction/input/key-layout-files)
6. **配置运行权限。** 分别核对 `/dev/uinput` 的 Linux 文件权限和 SELinux 权限，给桥接进程明确的用户或组，并授权所需的文件操作与 ioctl。也可为 uinput 配置独立标签，但先检查现有蓝牙或其他组件是否使用同一节点，并保留现有访问。读取内核 AVC 检查实际缺项。

### 验收命令

```bash
# 固定使用 SDK 版本的 ADB，并指定 H16 的序列号。
ADB_BIN="$HOME/Android/Sdk/platform-tools/adb"
ADB_SERIAL='e2d72141'

# 核对原厂通道服务和新桥接进程的启动状态。
"$ADB_BIN" -s "$ADB_SERIAL" shell 'getprop init.svc.rc_service; getprop init.svc.h16_input'

# 列出 Linux 输入设备及能力。找到 H16 RC Input 对应的 event 节点和两个 ABS 轴。
"$ADB_BIN" -s "$ADB_SERIAL" shell 'su 0 getevent -lp'

# 将 eventN 替换为上一步找到的设备。依次转两个旋钮并观察 EV_ABS 与 SYN_REPORT。
"$ADB_BIN" -s "$ADB_SERIAL" shell -tt 'su 0 getevent -lt /dev/input/eventN'

# 在 Android 输入服务中确认设备分类、轴和范围。若只有 getevent 有变化，优先检查这里。
"$ADB_BIN" -s "$ADB_SERIAL" shell dumpsys input | rg -n -A 30 'H16 RC Input'
```

判定通过的条件是每个旋钮只改变预期轴，输出方向和端点符合标定，普通应用收到轴值，同时设备的触屏和已有实体按键正常。

## 二、把风扇接入 Framework 系统服务

```text
特权客户端 → Binder h16_fan → H16FanService（system_server）
    → 私有本地套接字 → h16_fand → GPIO174 和温度节点
```

风扇执行进程负责唯一的运行时写入。Framework 服务负责 Binder 权限、查询和控制接口，GPIO I/O 留在独立服务域。先实现只读查询，再开放控制。交接旧温控服务时保留自动模式。

### 改哪些源码

| 文件 | 改动 |
| --- | --- |
| `device/skydroid/arowana_rc/h16_fan/Android.mk` 和 `h16_fand.cpp` | 新建设备端进程，读取 GPIO，序列化写入，回读结果，实现自动模式。 |
| `device/skydroid/arowana_rc/legacy-init/h16_fand.rc` | 定义服务和私有 Unix socket。用 init 的 `socket` 指令创建，进程通过 `android_get_control_socket()` 取得描述符。让 GPIO 已初始化后再开始接收控制。 |
| `device/skydroid/arowana_rc/skydroid_arowana_rc.mk`、`legacy-init.mk`、`sepolicy/` | 打包进程和 init 文件。为进程、socket 和可独立标记的 GPIO 节点定义权限，仅让 system_server 连接，限制 daemon 只访问必要节点。 |
| 当前 boot ramdisk 的 `init.arowana-rc.rc` | 核对 GPIO174 初始化顺序。功能交接后停用旧的 `service fan` 自动启动，避免两个进程争写。把变更保存到现有的 boot 打包流程，镜像更新后随 boot 一起发布。 |
| `frameworks/base/core/java/android/os/IH16FanService.aidl`、`frameworks/base/Android.mk` | 定义内部 Binder 接口并加入 AIDL 编译列表。 |
| `frameworks/base/services/core/java/com/android/server/H16FanService.java` | 继承 `SystemService`，用 `publishBinderService()` 发布 `h16_fan`，执行权限检查，设置 IPC 超时。 |
| `frameworks/base/services/java/com/android/server/SystemServer.java` | 只在 H16 产品上启动服务。以实机 `ro.product.device` 读数为准核对产品判定。 |
| `frameworks/base/core/res/AndroidManifest.xml`、`system/sepolicy/private/service_contexts` 及服务类型策略 | 声明签名权限，用 Binder 服务标签限制注册和查找。测试客户端按权限签名，读取和写入可使用不同权限。 |

### 接口行为和实现顺序

1. **先读状态。** GPIO 已配置为 `out` 后读取 `/sys/class/gpio/gpio174/value`。接口可返回 `ON`、`OFF`、`UNKNOWN`，同时提供当前模式和最后错误。根据实际读回返回结果。读失败、节点未就绪或后端失联时返回 `UNKNOWN`。说明 `ON` 表示 GPIO 使能，实际转动可通过现场观察确认。
2. **接入 Binder。** 可设计 `getFanState()`、`getFanMode()`、`setFanMode(mode)`，写入操作需要签名级权限。daemon socket 若使用流协议，要定义有边界的请求、应答长度和超时。socket 使用 Linux 文件权限、SELinux 和对端凭据校验，仅接受 system_server 发来的控制。连接或读写阻塞放到工作线程，并为请求设置超时，避免拖住 system_server。实现带权限检查的 `dumpsys h16_fan`，打印模式、GPIO 电平、最近一次温度和错误，方便 ADB 验收。
3. **保留自动温控。** 先核对原厂二进制读取哪些温度节点以及如何选用读数。原厂程序的默认阈值为高温 75 °C、低温 60 °C，默认周期 10 秒，需在实机验证。采用 `AUTO` 作为启动默认模式，高低阈值之间保持原状态。支持手动打开，测试用的手动关闭做成可超时的模式，并保留高温时自动启动的保护。温度读取连续失败时应报告错误并按保守策略维持散热。
4. **完成所有权交接。** 验证新进程读回 GPIO 并能维持 AUTO 后，将旧风扇服务从运行时写入路径移除。测试客户端只通过 Binder 操作。检查用户打开后能读到 `ON`，切回 AUTO 后能重新由温度决定状态。用可注入的温度数据验证阈值与回差，再做受控实机复核。

### 验收命令

```bash
# 核对 GPIO 标签、方向和当前输出，作为 Binder 返回状态的对照。
"$ADB_BIN" -s "$ADB_SERIAL" shell 'su 0 ls -lZ /sys/class/gpio/gpio174/value; cat /sys/class/gpio/gpio174/direction /sys/class/gpio/gpio174/value'

# 检查原生进程启动和 Binder 服务注册情况。
"$ADB_BIN" -s "$ADB_SERIAL" shell 'getprop init.svc.h16_fand; service list' | rg 'running|h16_fan'

# 查看在 H16FanService 中实现的诊断输出，重点对照模式、GPIO 读回和错误。
"$ADB_BIN" -s "$ADB_SERIAL" shell dumpsys h16_fan

# 查询两个新进程相关的 SELinux 拒绝。现有移植系统是 Permissive，能运行也要核对 AVC。
"$ADB_BIN" -s "$ADB_SERIAL" shell 'su 0 dmesg' | rg 'avc:.*(h16_input|h16_fan|rc_service)'
```

## 三、构建和刷机检查

```bash
# 选择 H16 的 AOSP 8.1 产品与既有构建环境。
source "$HOME/aosp/env_aosp8.sh" skydroid_arowana_rc-userdebug

# 构建镜像并实际安装新模块、InputFlinger、Framework 和产品配置。
# 首次接入应使用正常 systemimage 目标解析依赖。
make -j8 systemimage

# 编译 ramdisk 使用的 SELinux 策略和文件上下文。
make -j8 sepolicy file_contexts.bin plat_file_contexts nonplat_file_contexts
```

本设备用原厂内核和定制 ramdisk。使用当前移植的 boot 重打包流程，把新策略和需要修改的 init 声明合入 ramdisk。旋钮桥和风扇服务涉及新的执行标签，应配套使用同次构建的 `boot.img` 与 `system.img`。刷写前保存当前可启动的配对镜像并确认 Fastboot 产品名为 `arowana-rc`。刷写步骤参见 [Android 8.1 移植记录](../移植与故障/安卓8.1移植记录.md)。
